# SengenWinUI3 の設計

この文書は、SengenWinUI3 の層・公開する型の契約・部品の範囲・性能の測定の結果を、今の形で書く設計正本である。実装と食い違ったら、同じ変更の中でこの文書を直す。節「進み具合」だけは、作業の途中の状態を書く節であり、作業を終えたら消す。

## 命令が決めたこと

この節は、この作業(ONE.O.NET の issue #12 の「やることの1」)の命令が決めた境目と禁止を、理由とともに写す。兵士・検査員・参謀長は命令でなくこの文書を読むため、ここに写さない禁止は届かない。

| 決めたこと | 理由 |
|---|---|
| 式は本物の部品(画面に実際に出る WinUI の部品のオブジェクト)を直接組む。設計図(部品の種類と設定の値だけを持つ軽いデータの木)と差分の層は作らない | SengenUI も本物を直接組んでおり、差分の計算は作る費用と更新の費用の両方を足すため |
| 件数の多い一覧だけ、見えている行だけを作って使い回す部品(`ItemsRepeater` と自前の `IElementFactory`)で書く。どの件数から使い回しにするかは測って決める | 全部の行を本物で作ると、行数に比例して作る時間とメモリが増えるため |
| SengenWinUI3 は WinUI の部品をそのまま返さず、自前の型で包んで返す。包む費用が測って無視できないと分かったときだけ、葉の部品を本物で返す形へ寄せ、測った値をこの文書に書く | 利用する側が WinUI を直接触れないようにし、ONE.O.NET の規約(`csharp_coding_rules.md` 第9条の4)をコンパイラで守るため |
| 実行中に変わる値は、部品にモデルセル(値と、変わったときの知らせを持つもの)を渡し、部品が購読して変わったときだけ自分を更新する。購読は部品の破棄で解く | SengenImgui の `Text(() => 値)` に近い1行の書き味を保ちながら、変わったときだけ動く保持モード(部品のオブジェクトを保持し続ける描画の仕組み)の速さを保つため |
| 書き方の細部は SengenImgui の形に合わせる(型を保つ拡張メソッドのチェーン・`Tap`・`return ( ... )`・`sealed` の単位のクラス・静的な条件は `?:` と null・名前付きの見た目の定数と `With`)。名前は日本語にする | オーナーが SengenImgui で決めた書き方であり、ONE.O.NET の命名の規約に合わせるため |
| ONE.O.NET のコードを見ずに、WinUI 3 の薄い包みとして一般に必要な部品をそろえる。それより後に足りないと分かったものは、使われた形から足す | オーナーの指示(ONE.O.NET の issue #12 の1)。利用する側から逆算すると、一般の形でなく1つのアプリの形になるため |
| 段の順番を、(1) 共通の契約と測定、(2) 将軍への設計の確かめ、(3) 部品の幅を広げる、に固定する | 部品の数より契約のほうが、後の置き換えの書き味と費用を決めるため |
| 回帰テストは足さない。測る試作は書き捨てとして扱い、マージの前に消す | 命令の指定 |
| リポジトリは公開である。測定の結果は、比べる2つの値の比と Release のビルドであることだけを書き、測った PC の構成は書かない | PC と個人を特定できる情報を公開のリポジトリに書かないため |


## ONE.O.NET の規約から外れる所

SengenWinUI3 の C# の規約の正本は ONE.O.NET の `.claude/規約/コード/` にある。次の4か所は、オーナーが SengenUI と SengenImgui で決めた書き方に合わせるため、その規約の文から外れる。規約の文を直すのは、ONE.O.NET の画面を SengenWinUI3 へ置き換える任務で ONE.O.NET の側で行う。

| 規約の条 | 外れる所 | 理由 |
|---|---|---|
| `csharp_coding_rules.md` 第5条の1(null を「無し」の意味に使わない) | 子の配列の中の null を飛ばす(判断5)。`見た目` の項目は全部 null を許し、null は「当てない」を表す | SengenImgui の `守るべきテクニック.md` 第5条・第6条・第8条の書き方であり、構築の時に決まる条件を `条件 ? 部品 : null` の1つの式で書くため |
| 第6条の3と第9条の1(画面の木を `new` と初期化子の入れ子の式で書く) | 画面の木を、葉を作る関数と型を保つ拡張メソッドのチェーンで書く | SengenUI と SengenImgui の書き方であり、オーナーが「メソッドチェーンなどは同じにしたい」と決めたため |
| 第13条の3(材料から値を作る静的メソッドは `From〜`) | 葉の部品を作る関数の名前を、部品の型の名前と同じにする(`文章("…")`) | 判断4。この関数は値の型を作る関数でなく、画面の木を書くための語であるため |

## 目的

SengenWinUI3 は、WinUI 3 の画面を XAML でもデータバインディングでもなく C# の式で組むためのライブラリである。利用する側は、部品の木を1つの式で組み(構築)、操作と処理をつなぎ(配線)、表示を変えるときは部品の更新の操作を呼ぶか、部品にモデルセルを渡す(更新)。最終の目標は、オーナーが旧アプリの SengenUI と同じ書き味で、速いネイティブの画面を書けることである。

## 層の定義

SengenWinUI3 は2つのプロジェクトに分かれる。

| 層 | プロジェクトと名前空間 | 持つもの | 知ってよいもの |
|---|---|---|---|
| 状態 | `src/SengenWinUI3.状態/`(`net11.0`。Windows に依存しない)。名前空間 `SengenWinUI3.状態` | モデルセル・派生セル・購読の解除 | .NET の標準ライブラリだけ |
| 部品 | `src/SengenWinUI3/`(`net11.0-windows`)。名前空間 `SengenWinUI3` の1つ | 部品の包み・葉を作る関数・チェーンの拡張メソッド・見た目・長さと色の値・一覧の使い回し・浮かぶ部品・Composition の影とアニメーション | 状態の層と WinUI 3 |
| 利用する側 | ほかのリポジトリ(ONE.O.NET など) | 画面の単位のクラス(複合部品の派生)・状態・サービス | 状態の層と部品の層の公開の型。アプリの `Window` と `Application` のほかの WinUI の型は使わない |

- 状態の層を部品の層と別のプロジェクトにするのは、利用する側のサービスや状態の層がモデルセルを持つときに、WinUI への依存を持ち込まないためである。状態の層から部品の層を参照すると、プロジェクトの参照が循環してビルドが通らない
- 部品の層の名前空間を1つにするのは、利用する側が `using SengenWinUI3;` と `using static SengenWinUI3.宣言;` の2行で全部を使えるようにするためである

## 主要な設計判断

### 判断1: すべての部品は自前の基底 `部品` を継承した包みの型である

`部品` とは、画面の木に入れられるものすべての基底の型のことである。`部品` は本物の WinUI の部品を1つ持ち、その本物を `internal` でしか見せない。利用する側は、SengenWinUI3 が作った部品の本物へ触れる手段を持たない。`部品` のコンストラクタは `private protected` にし、SengenWinUI3 の外からは `複合部品`(判断2)だけを継承できる。

包む型で守れるのは、SengenWinUI3 が作った部品の本物へ触れないことだけである。利用する側はアプリの `Window` を持つため WinUI のパッケージを参照しており、WinUI の部品を自分で `new` する書き方はコンパイルで止まらない。それを止めるには、利用する側のプロジェクトに使うと警告になる API を列挙する解析器(`Microsoft.CodeAnalysis.BannedApiAnalyzers`)を入れる。これは置き換えの任務へ申し送る。

`TextBlock` と `Border` は WinUI の側で `sealed` であり継承できないので、葉の部品(本物を1つだけ持つ部品)は、継承でなく本物を持つ形で包む。継承できる WinUI の部品も、同じ形にそろえる。

### 判断2: 利用する側の画面の単位は `複合部品` の `sealed` の派生であり、根は初めて木へ入れるときに作る

`複合部品` とは、ほかの部品を組み合わせて1つの単位にした部品の基底のことである。派生のクラスは `protected override 部品 根を構築する() => ( ... );` で中身の木を返す。`複合部品` は `根を構築する()` を基底のコンストラクタから呼ばず、本物が初めて要ったとき(親の木へ入れるとき)に1回だけ呼ぶ。基底のコンストラクタから仮想メソッドを呼ぶと、派生のフィールドが初期化される前に派生の処理が走るためである(SengenImgui の `設計思想.md` 8.2 と同じ規律)。

`複合部品` は自分では WinUI の部品を増やさない。親の木へ入るのは `根を構築する()` が返した部品の本物である。構造だけの部品を1段増やすと、繰り返す行で費用が掛け算になるためである。`複合部品` に当てたチェーンの設定(余白・見た目など)は根の本物に当たり、根を構築した後に当てたものが効く。

C# の null 許容参照型を有効にしているので、`根を構築する()` の中で `Tap` を使ってフィールドへ部品を受ける書き方は、フィールドが null 許容になり成り立たない。後から更新したい子は、フィールドの初期化子で作って持ち、木の中にそのフィールドを置く。引数に依存する子は、主コンストラクタ(`sealed class 名前(引数) : 複合部品`)の引数をフィールドの初期化子で使って作る。これは SengenUI の「裸の部品をフィールドで持たず、拡張の型にする」規則とも合う。

### 判断3: チェーンは型を保つ拡張メソッドで書く

全部の部品に共通の設定は、`public static T 余白<T>(this T 部品, 有効画素 幅) where T : 部品` の形の拡張メソッドにする。`T` を受けて `T` を返すので、`文章("…").余白(8.画素).見た目(…)` とつないでも具象の型が保たれる。拡張メソッドは静的な関数なので、呼ぶたびに余分なオブジェクトを作らない。

一部の種類の部品だけが持つ設定は、その種類が実装する目印のインターフェースを制約に足した拡張メソッドにする(`where T : 部品, I子を持てる`)。目印のインターフェースの中身は `internal` にし、SengenWinUI3 の外からは実装できない形にする。1種類の部品だけが持つ設定は、その部品の型のメソッドにする。

### 判断4: 葉の部品は型と同じ名前の関数で作り、複合部品は `new` で作る

葉の部品(本物を1つ持つ部品・`出し分け`・`使い回す一覧`)は、静的クラス `宣言` の関数で作る。関数の名前は部品の型の名前と同じにする(`文章("…")`・`縦の並び()`・`ボタン("保存")`)。利用する側は `using static SengenWinUI3.宣言;` を置く。葉の部品のコンストラクタは `internal` にし、作り方を関数の1通りにする。利用する側の `複合部品` の派生は `new スロットカード(…)` で作る。

この分け方は、SengenUI のガイド第5条(LV1 は糖衣の関数で作り、LV1 拡張は `new` で作る)と、SengenImgui の `UI.cs`(`Text("…")`・`VStack()` を `using static` で取り込む)の2つの前例と同じである。型と同じ名前の関数を `using static` で取り込んでも、型の宣言と関数の呼び出しを同じファイルに並べてコンパイルが通ることを、固定した SDK で確かめた。

### 判断5: 子は配列で受け、null を飛ばす

子を持つ部品の `子を入れる(params 部品?[] 子List)` は、配列の中の null を飛ばす。構築の時に決まる条件は `条件 ? 部品 : null` で書く(SengenImgui の `守るべきテクニック.md` 第5条・第6条)。実行中に変わる条件は `出し分け`(判断8)で書く。

### 判断6: 実行中に変わる値はモデルセルで渡し、購読は部品の破棄で解く

状態の層の `モデルセル<T>` は値を1つ持ち、値が前と違う値に変わったときだけ購読者へ知らせる。`派生セル<T>` は、列挙したセルから計算で値を出し、元のセルが変わったときに計算し直す。部品は `I読めるセル<T>`(モデルセルと派生セルが実装する、読むことと購読することだけができるインターフェース)を受ける。

部品へセルを結ぶ書き方は3つある。値を見せる部品は、関数でセルを受ける(`文章(名前のセル)`)。入力の部品は、値のセルと、利用者が値を変えたときの処理の組を受ける(`文字入力(名前のセル, 名前を変える)`。SengenImgui の `TextField(getter, setter)` と同じ形)。それ以外は、拡張メソッド `購読する(セル, (自分, 値) => …)` で、部品と値を受ける処理を渡す。処理に部品自身を渡すのは、部品を捕まえるラムダを作らずに書けるようにするためである。どの書き方でも、購読の解除は部品が持ち、部品の `破棄する()` で解く。利用する側の画面の中では、セルの `購読する` を直接呼ばない。直接呼んで戻り値を捨てる誤りは、解析器の警告にならないためである。

スレッドの約束は次のとおりである。`モデルセル` の `Set値` は、どのスレッドから呼んでもよい。サービスは WinUI を知らず、別のスレッドで届いた値をそのまま設定するためである。セルは知らせを `Set値` を呼んだスレッドで同期して呼ぶ。部品の層の購読は、知らせを受けたスレッドが部品の UI スレッドでなければ、部品の `DispatcherQueue` へ処理を送り、送った先でそのときのセルの値を読み直して使う。届いた順が前後しても、最新の値で終わるためである。購読者が例外を投げたときは、セルは残りの購読者へ知らせ終えてから、起きた例外をまとめて投げる。1つの購読者の誤りで、ほかの部品の更新が黙って止まらないようにするためである。

モデルセルを部品に渡すことは、利用する側が何を表示に結ぶかを引数で明示する書き方であり、ONE.O.NET の規約第9条の3の「データバインディングを使わず明示する」に反しない(将軍の読み)。

### 判断7: 子の覚えと破棄のたどり方は基底の `部品` が1か所で持つ

`部品` は自分の親と、自分が持つ子の一覧を覚える。部品が子を本物のどの場所(`Panel.Children`・`Border.Child`・`ContentControl.Content`・浮かぶ部品の中身・`出し分け` の2つ・`複合部品` の根)へ入れても、基底の `internal` の操作で子として登録する。破棄でたどる経路はこの一覧だけである。

外す操作は2つだけにする。`親から外す()` は今の親から外すだけで、購読は残す(別の親へ入れ直せる)。`破棄する()` は、自分と子孫の購読を解き、子孫の覚えを捨て、破棄を始めた部品だけを親の本物から外す。子孫の本物は、破棄を始めた部品の本物ごと木から外れるので、1つずつ外さない。1つずつ外すと、子の数の2乗の手間になりうるためである。2回目の `破棄する()` は何もしない。破棄した後の部品へのほかの操作は、到達したらバグである状態として例外を投げる。親を持つ部品を別の親へ入れたときも例外を投げる。WinUI の部品は親を1つしか持てず、黙って外すと、どこで付け替えたかがコードから読めなくなるためである。

`複合部品` の派生は、自分で作ったタイマーや購読と、木に入れていないフィールドの部品を、`一緒に破棄する(…)` で預け、部品の破棄で一緒に解く。`ウインドウ.中身を置く(部品)` は、ウインドウが閉じたときに根の部品を破棄する。

### 判断8: 実行中に変わる条件と、作るのを遅らせる部品は `出し分け` で書く

`出し分け` とは、真偽のセルを受け、真のときの部品と偽のときの部品(省ける)の片方だけを見せる部品のことである。`出し分け` は自分の入れ物(`Grid`)を本物として持ち、2つの部品をその中に入れて、セルが変わったときに見える方を切り替える。親の側に「子の本物が替わった」を受ける約束を作らずに済ませるためである。入れ物の費用は1つの `出し分け` につき部品1つであり、繰り返す行での費用は測定で確かめる。

部品の代わりに部品を作る関数を受ける版(`出し分け(条件, () => 重い部品())`)は、その側が初めて見えることになったときに1回だけ関数を呼ぶ。めったに見せない重い部品を、起動の時に作らずに済ませるためである。SengenUI の `childIf` の `True: () => 子` とも同じ形になる。

### 判断9: 件数の多い一覧は `使い回す一覧` で書き、行は作るときに1回だけ配線する

`使い回す一覧<T項目, T行>` とは、`ItemsRepeater` を包み、見えている行の部品だけを作り、画面から外れた行の部品を別の項目で使い回す部品のことである。利用する側は、行の部品を作る関数(`Func<T行>`)を渡す。行の部品は `I使い回せる行<T項目>` を実装する。一覧は、行に項目を見せるときに `項目を見せる(項目)` を呼び、行が使い回しの待ちへ入るときと一覧の破棄のときに `項目から離れる()` を呼ぶ。行が項目の中のセルを購読するとき、`項目から離れる()` で解く。

`使い回す一覧` はスクロールを中に持たず、外側の `スクロール` の部品の中に置く。`ItemsRepeater` は外側のスクロールの見えている範囲で仮想化するので、中にスクロールを持つと、スクロールする画面の中に置いたときに2重のスクロールになるためである。末尾へ移ることと末尾に留まることは、`スクロール` の部品が持つ。外側のスクロールの中で使い回しが効くことは、一覧を書く単位の最初に動かして確かめる。

使い回された行は別の項目を見せるので、行の配線は作るときに1回だけ行い、行がいま見せている項目の ID をハンドラへ渡す(`on削除(ID)`)。行ごとの ID をラムダで捕まえる書き方は使えない。一覧は、項目を私有の箱の型に包んで `ItemsSource` へ渡す。項目が構造体でも、WinRT の境目を値のまま越えずに済ませるためである。

件数に上限の無い一覧(会話の履歴など)は、件数によらず `使い回す一覧` で書く。上限があり件数の少ない一覧は、子を持つ部品の `子を足す`・`子.破棄する()` と、利用する側の `Dictionary<ID, 行>` の手動の管理で書く(SengenUI と同じ)。上限のある一覧のどの件数から `使い回す一覧` にするかは、節「測定」の測定2で決める。

### 判断10: 見た目は名前付きの定数で共有し、当て方は部品の種類ごとに持つ

`見た目` とは、背景・文字の色・文字の大きさ・文字の太さ・枠線・角の丸み・内側の余白などを、全部 null を許す項目で持つ値のことである。null の項目は当てない。利用する側は `static readonly 見た目` の定数を並べ、`With(上書き)` で派生を作る。`見た目` がブラシ(WinUI が色を塗るときに使うオブジェクト)を作るのは、初めて部品へ当てるときに1回だけであり、同じ定数を当てた部品は同じブラシを共有する。色の項目の型は `union 塗り(色)` にする。後でテーマの色(明るい表示と暗い表示で替わる色)を `塗り` の場合に足しても、利用する側の定数を書き直さずに済ませるためである。

当て方は、`部品` の `internal virtual` の操作(案: `見た目を当てる(見た目)`)を部品の種類ごとに上書きして、その部品のファイルが持つ。部品を1種類足すときに、ほかの部品のファイルを書き換えずに済ませるためである。部品が持たない項目(`文章` の背景など)が null でない `見た目` を当てたら、到達したらバグである状態として例外を投げる。書いた見た目が黙って効かないと、利用する側は理由をコードから読めないためである。`複合部品` に当てた `見た目` は根へ渡す。どの項目がどの部品に効くかは README に表で書く。

### 判断11: 長さは `有効画素` の型で渡す

`有効画素` とは、WinUI が大きさと位置に使う単位(画面の拡大率で物理の画素へ換算される前の画素。英語で effective pixel)の長さを持つ値の型のことである。公開の関数は、幅・高さ・余白・間隔・文字の大きさを `double` でなく `有効画素` で受ける。ONE.O.NET の規約(`csharp_coding_rules.md` 第2条の3)が、単位の分からない `double` を境界の外へ渡さないと定めているためである。書き味を保つため、`12.画素` と書ける拡張のプロパティを `int` と `double` に持つ。`int` から `有効画素` への暗黙の変換は置かない。余白は `余白(8.画素)`・`余白(縦, 横)`・`余白(左, 上, 右, 下)`・`余白(四辺の長さ)` の4つの版を持つ。色は `色` の型で、寄せ方は自前の列挙で渡す。利用する側が WinUI の型(`Thickness`・`Color`・`HorizontalAlignment`)を書かずに済ませるためである。

### 判断12: 木へ入れられないポップアップは `浮かぶ部品` にし、チェーンで部品に付ける

`Flyout` と `MenuFlyout` は `FrameworkElement` でなく、`ContentDialog` は木へ入れずに出し、`ToolTip` は添付プロパティで部品に付ける。どれも画面の木の子にならないので、`部品` を継承させない。`浮かぶ部品` とは、木へ入れられず、ほかの部品に付けて出す部品の基底のことである。中身は `部品` で受け、浮かぶ部品の破棄で中身を破棄する。付け方は部品のチェーンにする(`押したら開く(ポップアップ)`・`右クリックのメニュー(メニュー)`・`説明("…")`)。確認の画面は、基準の部品から表示に要る `XamlRoot` を取る `見せる(部品 基準)` で出し、結果を `union` で返す。

### 判断13: 出来事は `On〜` で1つの部品に1回だけ受け、引数に WinUI の型を出さない

葉の部品の出来事は `On押された(Action 処理)` のように、`On` と出来事を表す句の名前のメソッドで受け、自分の型を返す。同じ部品に同じ `On〜` を2回呼ぶと例外を投げる(`配線ポート` の2回目の例外と同じ考え方)。出来事の引数に WinUI の型を出さず、要るときは自前の値の型で渡す。キー・ポインタ・大きさの変化の出来事は全部の部品のチェーンに置き、名前と引数の型を基底の単位が決める。並列の単位の兵士が別々に決めると、名前と形が割れるためである。

値を見せる部品は、関数で固定の値かセルを受け、さらに値を設定するメソッド(`Set文字(string)` のように `Set〜`)を持つ。セルに結んだ部品へ `Set〜` を呼ぶと例外を投げる。値の出どころを2つにしないためである。部品は、本物の今の値と等しい値を本物へ設定しない。入力の部品で、状態から流した値が本物の変更の知らせを起こし、また状態へ返る往復を止めるためである。

### 判断14: ウインドウへは拡張メソッドで置く

利用する側は、アプリの `Window` に `ウインドウ.中身を置く(部品)` で根の部品を置く。2回呼ぶと、前の根を破棄して置き換える。

### 判断15: トーストはウインドウに付けた `トースト置き場` が、画面の中身とポップアップより上に出す

トーストとは、画面の隅に一時的に出て、決めた時間が過ぎるか利用者が閉じると消える知らせのことである。`トースト置き場` とは、ウインドウに1つ付け、トーストを積んで出すものの型のことである。利用する側は `ウインドウ.トースト置き場を付ける(設定)` で置き場を得て、`置き場.出す(知らせ)` で出す。

- 置き場は画面の木の部品でなく、ウインドウの `XamlRoot` に付けた `Popup`(WinUI の、ほかの部品の上に重ねて出す層)で出す。`ウインドウ.中身を置く` で画面の中身を何度入れ替えてもトーストが残り、ポップアップと確認の画面が出ているときもトーストが見えるようにするためである。確認の画面より上に出ることは、トーストの単位で動かして確かめる
- トーストの無い所では、後ろの画面を押せる
- `トーストの知らせ` は、種類(成功・情報・警告・エラー)と文を必ず持ち、詳細・ボタン(文字と押したときの処理)・消え方(時間で消える・閉じるまで残る)・閉じるボタンの有無を `With〜` で足す値である。足さない項目は「無い」か置き場の既定であり、null で表さない
- `出す` は `トーストの札` を返す。札とは、出したトーストを後で閉じる・文を書き換えるための値のことである。置き場は全部を閉じる操作も持つ
- 位置・余白・幅・間隔・積む向き・出入りの動きの時間・種類ごとの既定の消える時間・同時に出す数の上限・種類ごとの見た目(色と印)は、`トースト置き場の設定` にまとめ、利用する側が渡す。既定の値は旧アプリと同じにする(右上・上と右から 20・幅 280〜350・間隔 10・新しいものが下・出入り 0.3 秒・消える時間は成功 3 秒・エラー 5 秒・警告 4 秒・情報 3 秒・上限なし)。色は SengenWinUI3 に旧アプリの色を埋め込まず、利用する側が `見た目` で渡す
- `出す` と札の操作は、どのスレッドから呼んでもよく、UI スレッドでないときは置き場の `DispatcherQueue` へ送る。例外の知らせのように、別のスレッドで起きた出来事から出すためである
- 同じ知らせを重ねて出さない抑えと、文言と番号の持ち方は、利用する側(ONE.O.NET)が決める。何が同じ知らせかは利用する側の知識であるためである

## 境目の契約

この節は、単位をまたいで使う型と関数の形を決める。公開の型に加え、全部の部品が従う `internal` の約束(節「部品の内側の約束」)も境目に入る。単位の内側の細部(フィールド・私有の関数・内部の型)は、書く兵士が決める。名前は案であり、節「進み具合」の判断事項で確かめを受ける。

### 状態の層

```csharp
namespace SengenWinUI3.状態;

public interface I変わるセル
{
    IDisposable 購読する(Action 処理); // 値が変わったときに呼ぶ。返した値を Dispose すると解く
}

public interface I読めるセル<out T> : I変わるセル
{
    T 値 { get; }
    IDisposable 購読する(Action<T> 処理); // 値が変わったときに新しい値で呼ぶ
}

public sealed class モデルセル<T> : I読めるセル<T>
{
    public モデルセル(T 初期値);
    public void Set値(T 新しい値); // どのスレッドから呼んでもよい。前の値と EqualityComparer<T>.Default で等しければ知らせない
}

public sealed class 派生セル<T> : I読めるセル<T>, IDisposable
{
    public 派生セル(Func<T> 計算する式, params I変わるセル[] 元のセルList); // 元のセルの値の型が違っても列挙できるよう、型引数の無いインターフェースで受ける
    public void Dispose(); // 元のセルへの購読を解く
}
```

- 購読者の一覧は、購読と解除のたびに新しい配列へ差し替え、知らせる側は差し替える前の配列を読む。知らせの途中の購読と解除と、別のスレッドからの `Set値` で、一覧が壊れないようにするためである
- 購読者が例外を投げたら、残りの購読者へ知らせ終えてから、起きた例外を `AggregateException` にまとめて投げる

### 部品の層の基底

```csharp
namespace SengenWinUI3;

public abstract class 部品
{
    private protected 部品();
    public void 親から外す();
    public void 破棄する();
}

public abstract class 複合部品 : 部品
{
    protected 複合部品();
    protected abstract 部品 根を構築する();           // 初めて本物が要ったときに1回だけ呼ばれる
    protected void 一緒に破棄する(IDisposable 解くもの); // 部品の破棄で一緒に Dispose する
    protected void 一緒に破棄する(部品 木の外の部品);   // 木に入れていないフィールドの部品を預ける
}

public abstract class 浮かぶ部品
{
    private protected 浮かぶ部品();
    public void 破棄する();
}

public sealed class 配線ポート<T配線> where T配線 : class
{
    public 配線ポート(string 所有者の名前);
    public void 配線する(T配線 配線); // 2回目は例外
    public T配線 先 { get; }           // 未配線なら例外
}

public interface I配線可能<T自分, T配線> where T自分 : I配線可能<T自分, T配線>
{
    T自分 配線する(T配線 配線);
}

public static partial class 宣言 { /* 葉の部品を作る関数。部品の種類ごとのファイルに partial で置く */ }
```

`宣言` を `partial` にするのは、部品を1種類足す単位が、自分の部品の関数を自分のファイルに置き、ほかの単位のファイルを書き換えずに済ませるためである。

### 部品の内側の約束

全部の部品が従う `internal` の約束である。名前は案であり、形は契約の単位の兵士が決めて、この節を大佐が直す。

| 約束 | 形 |
|---|---|
| 本物 | `部品` は `internal abstract FrameworkElement 本物 { get; }` を持つ。`複合部品` は根の本物を返し、初めて読まれたときに根を構築する |
| 子の登録 | `部品` は `internal` の操作で子を登録し、手放す(案: `子として持つ(部品)`・`子として手放す(部品)`)。親の覚えと子の一覧は基底が持つ。本物のどこへ入れたかに関係なく、子を持つ部品は全部これで登録する |
| 破棄 | 基底の `破棄する()` が子の一覧をたどり、子孫の購読を解き、破棄を始めた部品だけを親の本物から外す。部品の種類ごとの後片付けは `internal virtual` の操作(案: `破棄のときに片付ける()`)で足す |
| 購読 | 基底は購読の解除(`IDisposable`)の一覧を持ち、破棄で解く。部品の層の購読は判断6のスレッドの約束に従う |
| 見た目 | `部品` は `internal virtual void 見た目を当てる(見た目)` を持つ。既定の当て方は、全部の部品に効く項目が無いので、null でない項目があれば例外を投げる。部品の種類ごとに上書きする。`複合部品` は根へ渡す |
| 中身を1つ持つ部品 | `枠`・`スクロール`・`ボタン`(中身に部品を置くとき)は `I子を持てる` を実装せず、その型のメソッド `中身を置く(部品)` を持つ。`I子を持てる` を実装するのは本物が `Panel` の部品だけである |

### 葉の部品の形

- 葉の部品は `public sealed class 名前 : 部品` で、本物を1つ持ち、コンストラクタは `internal` にする。作る関数は `宣言` に置き、関数の名前は型の名前と同じにする
- 値を見せる部品は、固定の値を受ける関数と `I読めるセル<T>` を受ける関数の両方を持ち、値を設定する `Set〜` を持つ(判断13)
- 入力の部品は、値のセルと利用者が変えたときの処理(`Action<T>`)の組を受ける関数を持つ。セルを持たない使い方として、値を受けない関数と `On〜が変わった(Action<T>)` も持つ
- 出来事は判断13のとおり `On〜` で受ける
- 毎フレームや一覧の行の更新のたびに走る処理では、ラムダ・配列・文字列を作らない。組む時だけ走る処理は気にしない

## 部品の層の中の置き場所

## 測定

測定は、見本のアプリ(`samples/見本/`)の中の書き捨ての場面(`samples/見本/計測/`)で、Release のビルドで行う。測定の場面は、結果をこの節へ写した後に消す。結果は、比べる2つの値の比で書き、測った PC の構成は書かない。測るのは、基底を最終の形(親の覚え・子の一覧・購読の一覧を持つ形)で書いた後である。

| 番号 | 何を比べるか | 決めること | 決め方 |
|---|---|---|---|
| 1 | `TextBlock` を 1000 個と 10000 個、本物を直接作って `StackPanel` へ入れる場合と、`文章` の包みを通して `縦の並び` へ入れる場合の、作って最初に描かれるまでの時間と管理されたメモリの増え方 | 包む型のままにするか | 10000 個で、時間かメモリの差が 10% を超えたら、葉を本物で返す形を将軍へ上げる。超えなければ包む型で決まる |
| 2 | 文字と画像とボタンを持つ行を 100・1000・5000 件、`縦の並び` に全部作る場合と、`スクロール` の中の `使い回す一覧` で出す場合の、作って最初に描かれるまでの時間と管理されたメモリ。スクロール中の UI スレッドのフレームの間隔は記録だけする | 上限のある一覧で使い回しにする件数の境目 | 全部作る場合に、作って最初に描かれるまでが 100 ミリ秒を超えるか、管理されたメモリが使い回す一覧の 10 倍を超える最小の件数を境目にする |
| 9 | 1000 個の `文章` へ、モデルセルの購読で値を流す場合と、毎フレーム `Func` を読み直して変わったときだけ設定する場合の、値が変わらないフレームの UI スレッドの時間 | 判断6の確かめ | 結果は購読の側が時間を使わないことが前もって分かっており、判断を変えない。命令の指定なので測り、オーナーへ差を数で見せるために使う |
| 破棄 | 1000 個の子を持つ `縦の並び` を破棄する時間と、同じ数の子を1つずつ `破棄する()` した時間 | 判断7の破棄の作りのままでよいか | 1つずつの時間が件数の2乗で伸びるなら、少ない一覧の行の捨て方を README で `子を全部破棄する` に寄せる |
| 出し分け | `出し分け` を1つ持つ行を 1000 件作る時間と、持たない行を 1000 件作る時間 | 判断8の入れ物の費用 | 差が 20% を超えたら、繰り返す行の中では `出し分け` を使わず `見えるか` で切り替えるよう README に書く |

結果は、測った後にこの節へ写す。

## この段階でやらないこと

- 設計図と差分の層を作らない。命令の決定であり、差分の費用を引き受けないためである
- 部品の表で外した部品を作らない。一般の形を決める材料が無く、使われた形から足すためである
- XAML のリソースの辞書(テーマの色)の読み込みを包まない。ONE.O.NET の規約が XAML をリソースの辞書に使うことを許しており、テーマの色をどう渡すかは使われた形から決めるためである
- 回帰テストを足さない。命令の指定である
